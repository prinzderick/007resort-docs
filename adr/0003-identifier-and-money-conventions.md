# ADR-0003: UUIDv7 for sync-sensitive rows, DECIMAL for money, UTC everywhere

Status: Proposed
Date: 2026-09-22
Deciders: Architecture review (pending)

## Problem

The platform runs two independent MySQL instances (site, cloud) that must eventually agree on a shared history of records created on either side, and it processes real money across many concurrent terminals. Both facts constrain the identifier and numeric type choices from the very first migration, so getting them wrong is expensive to fix later.

## Decision

- **Identifiers on sync-sensitive tables**: UUIDv7, generated by the API, stored as `BINARY(16)`. UUIDv7 is time-ordered, which keeps InnoDB clustered-index inserts sequential (unlike UUIDv4, which fragments the index) while still guaranteeing global uniqueness without a central sequence — required once two databases can both originate new rows for the same table.
- **Money**: `DECIMAL(19,4)` plus a `currency_code`. Never `FLOAT`/`DOUBLE`. The API serializes money as a decimal string, never a JSON number, so no client language's floating-point parsing can introduce rounding error.
- **Time**: `DATETIME(6)` in UTC in storage; the API emits ISO-8601 UTC (`...Z`); local time is applied only at the presentation layer (POS receipt, admin UI).

See [04 §1](../architecture/04-database-schema.md#1-conventions-adr-0003) for the full convention table.

## Alternatives considered

- **`BIGINT AUTO_INCREMENT` everywhere, with a central id-allocation service for sync.** Rejected: adds an availability dependency (the id service) to every write path, precisely where local-first independence matters most.
- **UUIDv4** for sync-sensitive rows. Rejected: random UUIDs as InnoDB primary/clustering keys cause significant insert amplification and page fragmentation at volume; UUIDv7 gives the same global-uniqueness property with much better write locality.
- **Store money as integer minor units (kobo/cents).** A reasonable alternative to `DECIMAL`; not chosen because `DECIMAL(19,4)` is explicitly required by the specification and keeps amounts human-readable in the database without a conversion step, while still being exact.

## Consequences

- `BIGINT AUTO_INCREMENT` remains acceptable for purely local reference/lookup tables that never need a global identity (e.g. seeded catalogs like `capability_type`), decided per table at migration-review time.
- Every client and report must treat money as a decimal type / string, never parse it into a language's native floating-point number for arithmetic — called out explicitly in each repository's `CONTRIBUTING.md`.
