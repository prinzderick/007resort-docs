# 04 — Initial MySQL Schema Design

Status: **DRAFT for review**. The authoritative schema and migrations will live only in `otueke-api` (`db/migrations/`). This document and [`database/schema-draft-v0.sql`](../database/schema-draft-v0.sql) are the design proposal used to review that first migration before it is written; once the review lands, `otueke-api` is the single source of truth and this file is updated to link to it rather than duplicate it.

## 1. Conventions ([ADR-0003](../adr/0003-identifier-and-money-conventions.md))

| Concern | Convention |
| --- | --- |
| Engine | InnoDB, `utf8mb4` / `utf8mb4_0900_ai_ci` |
| Server time zone | UTC (`default-time-zone='+00:00'`) |
| Timestamps | `DATETIME(6)` in UTC. Every table has `created_at`, `updated_at`; mutable-header tables also have `row_version INT UNSIGNED NOT NULL DEFAULT 1` for optimistic concurrency |
| Primary keys, sync-sensitive tables | UUIDv7, generated by the API, stored `BINARY(16)`, exposed to clients as canonical `8-4-4-4-12` strings. UUIDv7 keeps inserts roughly time-ordered, which InnoDB clustered indexes need for write locality |
| Primary keys, local reference/config tables | `BIGINT UNSIGNED AUTO_INCREMENT` is acceptable where the row never needs a global identity (e.g. `permission`, `tax_rate` lookups) — decided per table in the migration review |
| Money | `DECIMAL(19,4)` plus a `currency_code CHAR(3)`. Never `FLOAT`/`DOUBLE` |
| Quantities | `DECIMAL(14,3)` (supports fractional units, e.g. kg) |
| Booleans | `TINYINT(1)` via the ORM's bool mapping |
| Enums | `VARCHAR` with a `CHECK` constraint (MySQL 8.4 enforces `CHECK`), not native `ENUM`, so adding a value is a data-compatible migration, not a column rebuild |
| Soft delete | Only on records users expect to "remove" from view but that must remain referenceable: `product`, `staff`, `role_assignment`, `bookable_resource`. Column `deleted_at DATETIME(6) NULL` + application-level filtering. **Never** on financial or audit tables — those are immutable and simply superseded by reversal rows |
| Multi-tenancy | `organization_id`, `site_id` on every operational table; `facility_unit_id` where applicable. Phase 1 has one row in `organization` and one in `site` |
| Foreign keys | Declared and enforced (`ON DELETE RESTRICT` by default; `CASCADE` only for true child rows like order lines) |
| Indexing | Every FK indexed; covering indexes added for the hot queries in [15](15-api-conventions-and-endpoint-map.md); reporting-heavy tables get a documented secondary index reviewed per migration |
| Idempotency | `idempotency_record(scope, idempotency_key)` unique, storing a hash of the request and a copy of the result, TTL-cleaned |
| Sync metadata | `sync_state ENUM-like VARCHAR` (`LOCAL,QUEUED,SYNCING,SYNCED,CONFLICT,FAILED`), `origin_node_id`, `version` (Lamport-style counter) on sync-sensitive tables |
| Audit | `audit_log` is append-only: insert-only grants for the application DB user, `prev_hash`/`row_hash` chain computed by the API |

## 3. Highest-risk tables, in detail

### 3.1 `slot_allocation` — prevents double booking

```sql
CREATE TABLE slot_allocation (
  id               BINARY(16) NOT NULL PRIMARY KEY,
  organization_id  BINARY(16) NOT NULL,
  site_id          BINARY(16) NOT NULL,
  resource_id      BINARY(16) NOT NULL,
  unit_no          SMALLINT UNSIGNED NOT NULL DEFAULT 1,
  slot_start       DATETIME(6) NOT NULL,
  slot_end         DATETIME(6) NOT NULL,
  booking_item_id  BINARY(16) NOT NULL,
  status           VARCHAR(16) NOT NULL DEFAULT 'HELD'
                     CHECK (status IN ('HELD','CONFIRMED','CANCELLED')),
  hold_expires_at  DATETIME(6) NULL,
  created_at       DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  CONSTRAINT uq_slot UNIQUE (resource_id, unit_no, slot_start)
) ENGINE=InnoDB;
```

The uniqueness constraint is the actual double-booking guard, not application logic. A `HELD` row reserves the slot for a short TTL while payment completes; an expiry sweeper cancels unpaid holds. Confirming two competing holds for the same slot is a constraint violation on the second `INSERT`/`UPDATE`, which the service maps to `409 Conflict`.

### 3.2 `entitlement_item` / `redemption` — prevents double redemption

```sql
CREATE TABLE entitlement_item (
  id              BINARY(16) NOT NULL PRIMARY KEY,
  entitlement_id  BINARY(16) NOT NULL,
  kind            VARCHAR(16) NOT NULL CHECK (kind IN ('ACCESS','RENTAL','GOODS','SERVICE')),
  facility_unit_id BINARY(16) NULL,
  qty             DECIMAL(14,3) NOT NULL,
  qty_redeemed    DECIMAL(14,3) NOT NULL DEFAULT 0,
  valid_from      DATETIME(6) NULL,
  valid_until     DATETIME(6) NULL,
  CHECK (qty_redeemed <= qty)
) ENGINE=InnoDB;

CREATE TABLE redemption (
  id                 BINARY(16) NOT NULL PRIMARY KEY,
  entitlement_item_id BINARY(16) NOT NULL,
  action             VARCHAR(16) NOT NULL CHECK (action IN ('ENTRY','EXIT','RELEASE','RETURN')),
  qty                DECIMAL(14,3) NOT NULL,
  device_id          BINARY(16) NOT NULL,
  staff_id           BINARY(16) NULL,
  created_at         DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
) ENGINE=InnoDB;
```

A redemption is recorded by an atomic conditional update:

```sql
UPDATE entitlement_item
   SET qty_redeemed = qty_redeemed + :qty
 WHERE id = :id AND qty_redeemed + :qty <= qty;
-- affected rows = 0  =>  reject as USED / exceeds entitlement, do not insert the redemption row
```

Two scanners hitting the same entitlement race on this single-row update; InnoDB serializes it, exactly one succeeds.

### 3.3 `provider_event` and `idempotency_record` — duplicate payment protection

```sql
CREATE TABLE provider_event (
  id                BINARY(16) NOT NULL PRIMARY KEY,
  provider          VARCHAR(32) NOT NULL,
  provider_event_id VARCHAR(128) NOT NULL,
  payload_hash      CHAR(64) NOT NULL,
  received_at       DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  payment_id        BINARY(16) NULL,
  CONSTRAINT uq_provider_event UNIQUE (provider, provider_event_id)
) ENGINE=InnoDB;

CREATE TABLE idempotency_record (
  scope             VARCHAR(64) NOT NULL,
  idempotency_key   VARCHAR(128) NOT NULL,
  request_hash      CHAR(64) NOT NULL,
  response_status   SMALLINT UNSIGNED NOT NULL,
  response_body     JSON NOT NULL,
  created_at        DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (scope, idempotency_key)
) ENGINE=InnoDB;
```

A duplicate webhook or a client retry hits the unique key, the second attempt returns the first result without re-executing the effect.

### 3.4 `stock_movement` / `stock_balance` — concurrent stock deductions

```sql
CREATE TABLE stock_movement (
  id               BINARY(16) NOT NULL PRIMARY KEY,
  item_id          BINARY(16) NOT NULL,
  location_id      BINARY(16) NOT NULL,
  qty_delta        DECIMAL(14,3) NOT NULL,     -- signed
  reason           VARCHAR(24) NOT NULL,       -- RECEIPT, TRANSFER_OUT, TRANSFER_IN, SALE, WASTAGE, ADJUSTMENT, COUNT, RENTAL_OUT, RENTAL_IN
  reference_type   VARCHAR(32) NOT NULL,
  reference_id     BINARY(16) NOT NULL,
  actor_staff_id   BINARY(16) NULL,
  created_at       DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
) ENGINE=InnoDB;

CREATE TABLE stock_balance (
  item_id      BINARY(16) NOT NULL,
  location_id  BINARY(16) NOT NULL,
  qty_on_hand  DECIMAL(14,3) NOT NULL DEFAULT 0,
  row_version  INT UNSIGNED NOT NULL DEFAULT 1,
  PRIMARY KEY (item_id, location_id)
) ENGINE=InnoDB;
```

A sale posts the movement and updates the balance in the same transaction, under a row lock (`SELECT ... FOR UPDATE` on `stock_balance`, or a single conditional `UPDATE ... WHERE qty_on_hand - :qty >= 0` when the location disallows negative stock). Two concurrent sales against the last unit serialize on that row; the loser gets `409 Conflict` / `422 Insufficient stock`, mapped by the service to a clear POS message. `stock_balance` is a projection: it can always be rebuilt from `SUM(qty_delta)` in `stock_movement`, and a nightly job checks the two agree.

### 3.5 `audit_log` — tamper-evident

```sql
CREATE TABLE audit_log (
  id              BINARY(16) NOT NULL PRIMARY KEY,
  occurred_at     DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  actor_staff_id  BINARY(16) NULL,
  facility_unit_id BINARY(16) NULL,
  operating_point_id BINARY(16) NULL,
  device_id       BINARY(16) NULL,
  action          VARCHAR(64) NOT NULL,
  entity_type     VARCHAR(64) NOT NULL,
  entity_id       BINARY(16) NOT NULL,
  old_value       JSON NULL,
  new_value       JSON NULL,
  approval_id     BINARY(16) NULL,
  prev_hash       CHAR(64) NOT NULL,
  row_hash        CHAR(64) NOT NULL   -- SHA-256(prev_hash || canonical(this row))
) ENGINE=InnoDB;
```

The application DB user has `INSERT` but not `UPDATE`/`DELETE` on `audit_log`. Each row's `row_hash` chains from the previous row's hash, so any tampering breaks the chain and is detectable by a periodic verification job.

## 4. Reporting access

Phase 1 reporting reads directly from the operational schema through **read-only SQL views** owned by `otueke-api` (e.g. `v_facility_daily_summary`, `v_cashier_shift_report`). `otueke-admin-web` connects with a read-only, view-restricted database credential — never with write access, and never joining raw ledger tables directly (see [ADR-0007](../adr/0007-php-apps-are-api-clients-without-business-data.md)). If reporting load becomes material, a replica or a dedicated reporting store is introduced by a new ADR rather than by PHP acquiring write access.
