# 24 — Failure Mode Matrix

Status: **DRAFT, awaiting review**. Every critical workflow's failure behavior, made explicit rather than assumed.

| Failure | Detected by | Local behavior | Cloud behavior | Recovery |
| --- | --- | --- | --- | --- |
| Cloud unavailable (VPS down or unreachable) | Local's outbox worker gets connection errors; heartbeat fails | All Local-authoritative operations continue normally (POS, KDS, attendance, local stock, ticket validation); offline-allocation bookings switch to their configured strategy | N/A (Cloud is the thing that's down) | Outbox drains automatically once Cloud is reachable again; no manual replay needed for normal-volume backlogs |
| Local unavailable (property internet or server down) | Cloud's heartbeat monitor marks the site `OFFLINE` after missed consecutive heartbeats | N/A (Local is down) | Immediate-fulfilment online orders blocked per [Booking Authority §4](sync/booking-authority-and-offline-allocation.md#4-immediate-online-orders); future bookings continue per the resource's configured offline-allocation policy; remote reporting shows the staleness explicitly | Local resumes heartbeating on recovery; Cloud's outbound-queued events (for Local) drain to it |
| Property internet unavailable (Starlink/ISP down, server itself fine) | Same as "Local unavailable" from Cloud's perspective — the two are indistinguishable to Cloud, and don't need to be distinguished for correctness | All physical operations continue fully (this is the primary scenario the local-first design exists for) | Same as "Local unavailable" above | Same as above |
| Redis unavailable (either node) | Laravel queue/cache calls fail; app-level health check | Outbox events remain durable in MySQL (queue jobs simply can't be dispatched until Redis returns) — **no committed transaction is lost**, only sync delayed | Same | Queue worker resumes processing once Redis is back; no data loss window |
| Queue worker process stopped (either node) | Process supervisor (see [Windows Local Server spec](26-windows-local-server-deployment.md) / [VPS spec](25-vps-production-deployment.md)) detects the process is down and restarts it | Same durability guarantee as Redis unavailable — MySQL-backed outbox means a stopped worker delays, never loses | Same | Supervisor auto-restart; outbox backlog processes once resumed |
| Synchronization failure (event repeatedly fails to apply) | `outbox_event.retry_count` exceeds a threshold, or `inbox_event.result = 'FAILED'` | Event surfaces in the sync observability view ([Heartbeat/Node Health §4](sync/heartbeat-and-node-health.md#4-observability-requirements)) rather than retrying forever silently | Same | IT/Admin investigates and uses the controlled retry/reprocess action, or escalates as a genuine conflict |
| Duplicate event delivery (network retry, or a queued-twice bug) | `inbox_event.event_id` uniqueness | N/A — receiver-side | N/A — receiver-side | Automatic: the duplicate is a no-op by design (see [Outbox/Inbox Design §3](sync/outbox-inbox-design.md#3-receiving-path-inbox)); no operator action needed |
| Out-of-order event arrival | `entity_version` gap detected by the applier | N/A — receiver-side | N/A — receiver-side | Automatic: deferred and retried until the intermediate version arrives, or escalates to `ENTITY_VERSION_CONFLICT` after a timeout ([Conflict Resolution Matrix](sync/conflict-resolution-matrix.md)) |
| Conflicting entity version (configuration/staff roster edited on both nodes) | Version check on inbox apply | Rejected event recorded as `CONFIGURATION_CONFLICT`/`PERMISSION_CONFLICT` | Same | Manual review and re-apply by Manager/IT ([Conflict Resolution Matrix](sync/conflict-resolution-matrix.md)) |
| Repeated payment provider callback | `provider_event` unique constraint (unchanged from the original design, [architecture/04 §3.3](04-database-schema.md#33-provider_event-and-idempotency_record--duplicate-payment-protection)) | N/A — Cloud-side | Duplicate callback is a no-op; original result replayed | Automatic |
| Stale heartbeat | Cloud's scheduled staleness check | N/A | Immediate-fulfilment online ordering degrades per resource policy; rest of the site unaffected | Automatic once heartbeats resume; no manual re-enable needed unless a resource was set to require manual re-enable |
| Partial network failure (some requests succeed, some time out) | Per-request timeout + retry with backoff in the outbox worker | Business transaction already committed locally regardless of network state — nothing to lose | Same | Retries with exponential backoff; idempotency makes retries safe |
| Real-time/WebSocket failure (KDS disconnects from Local's broadcaster) | Client-side connection state | KDS shows a clear "reconnecting" state and reloads the full ticket list on reconnect (per [007resort-kds](https://github.com/prinzderick/007resort-kds) design already in place) rather than assuming its last-known board state is current | N/A (real-time is Local-only, per [Domain Authority Matrix](23-domain-authority-matrix.md)) | Automatic reconnect with backoff |

## Principle

Every row above resolves to one of: **(a) the failure is invisible to business correctness** (most rows — durability via MySQL-backed queues and idempotency), **(b) the failure degrades one specific, narrow capability explicitly** (immediate online orders, a specific resource's online availability), never the whole system, or **(c) the failure surfaces for a human to resolve**, with enough detail to actually act, never silently.
